Data flows one way, from a server to the screen:

<Pipeline />

Each server gets its own thread, which connects, subscribes to the topics the app wants, decodes
messages, and reconnects when the connection drops. Decoders turn message bytes into scene types,
so nothing after them knows about message types. Decoded events wait in an inbox for the UI thread;
point clouds and images keep only the newest per topic, and everything else stays in order, because
order matters for TF. The UI thread applies the events, works out what to draw, and lays out the
panels. The 3D view is rendered offscreen and composited into its panel.

## Files

| File | Owns |
| --- | --- |
| `src/source.rs` | The `Source` trait; `FoxgloveWs`, the WebSocket client thread (tungstenite): subscribes to what the app wants, reconnects |
| `src/decode/` | The `(encoding, schema)` → decoder table; ROS CDR, Foxglove protobuf and JSON decoders; point field extraction; image decoding (`image.rs`) |
| `src/scene.rs` | What gets drawn, independent of message types: clouds, transforms, poses, scene entities, images, the TF tree |
| `src/connection.rs` | One server: its source and what it has received (clouds, TF, poses, scene entities, joints, images, text, stats), with pose and entity expiry, deletions and trails |
| `src/app.rs` | App state: opens and closes connections to match settings, resolves each panel's topics and subscribes to the union of what the panels show (`wanted`), loads the robot (file or description) and the models objects name, derives the display. `State::v3()` gives the 3D panel's settings. Images are kept per topic shown and annotated per view. |
| `src/annotate.rs` | Draws image annotations into the image on the CPU |
| `src/robot/` | URDF parsing and forward kinematics (`urdf.rs`), loading a robot's visuals into one mesh (`mod.rs`) |
| `src/mesh/` | Meshes: STL, glTF and GLB (`gltf.rs`), shapes, smoothed normals, mesh path resolution |
| `src/objects.rs` | Scene entities as parts of one mesh, placed per frame, plus their lines and text; the model cache |
| `src/settings.rs` | `Settings`, saved to settings.json: the connections and the layout. Each panel type's settings: `View3dSettings`, `ImageSettings`, `DataSettings` |
| `src/layout.rs` | The panel layout: the tree of panels (each with its settings), rows and columns, its file format and checks, the edits (split, close, show, swap, move a divider), presets and how they keep panel settings (`adopt`) |
| `src/panels.rs` | Draws the layout: the tiled panels, the dividers, each panel's header (its drag handle, settings button and menu), dragging a panel, and the Image, Data and Topics panels |

## Add a message type

A message that maps onto something Lantern already draws (a cloud, transforms, poses or joint
positions) needs one function and one table row. For example, `geometry_msgs/msg/PoseWithCovarianceStamped`,
which AMCL publishes on `/amcl_pose`:

<Steps>

1. Write the decoder in `src/decode/ros.rs` (ROS 2 CDR) or `src/decode/foxglove.rs` (Foxglove
   protobuf). It takes the message bytes and returns a `Decoded`.

   ```rust title="src/decode/ros.rs"
   /// `geometry_msgs/PoseWithCovarianceStamped`: the pose; the covariance after it is ignored.
   pub fn pose_with_covariance_stamped(bytes: &[u8], _: &ColorChoice) -> Result<Decoded, DecodeError> {
       let mut r = Cdr::new(bytes)?;
       let frame_id = header(&mut r)?;
       Ok(Decoded::Poses(Poses { frame_id, items: vec![Tracked::at(pose(&mut r)?)] }))
   }
   ```

2. Add a row to `DECODERS` in `src/decode/mod.rs`. The `Kind` decides its badge and which panels
   draw it. The third field restricts the row to topics with that name (alone or after a `/`, like
   the `robot_description` rows); `None` matches any topic.

   ```rust title="src/decode/mod.rs" ins={3}
   const DECODERS: &[Decoder] = &[
       // ...
       row("cdr", "geometry_msgs/msg/PoseWithCovarianceStamped", None, Kind::Poses, ros::pose_with_covariance_stamped),
   ];
   ```

3. Test it against bytes from the reference serializer. `scripts/capture_test_bytes.py` writes
   rclpy's CDR and the Foxglove Python SDK's protobuf into `src/decode/testdata/`. Add your message
   there and assert on the decoded values in the tests in `src/decode/mod.rs`.

</Steps>

The topic then gets a **Poses** badge and a switch on the 3D view's Poses tab.

A message that needs a new kind of drawing, such as a marker array, needs more: a `Decoded` variant
and `Kind`, a scene type in `src/scene.rs`, state in `src/connection.rs` and `src/app.rs`, and
drawing code in the viewport or the UI.

## Add a panel type

A panel is a `PanelKind` variant, a `Panel` variant that carries its settings, and functions that
draw it and its settings from app state. For example, a panel that lists joint positions, with
settings for the joints it leaves out:

<Steps>

1. Add the variant in `src/layout.rs`, with its file name (`id`), its `label`, and an entry in
   `ALL`. The compiler catches a missing `id` or `label`, but not a missing `ALL` entry, which is
   what puts the panel in the panel menus and the file format.

   ```rust title="src/layout.rs" ins={4}
   pub enum PanelKind {
       View3d,
       // ...
       Joints,
   }
   ```

2. Give it a settings type in `src/settings.rs` and a `Panel` variant that carries it. With
   `default`, a file can leave keys out; with `deny_unknown_fields`, a misspelt key is an error.
   A panel with no settings is a unit variant, like `Topics`.

   ```rust title="src/settings.rs"
   /// A Joints panel's settings.
   #[derive(Clone, Debug, Default, PartialEq, Serialize, Deserialize)]
   #[serde(default, deny_unknown_fields)]
   pub struct JointsSettings {
       /// Joints not listed (new joints are listed).
       pub hidden: BTreeSet<String>,
   }
   ```

   ```rust title="src/layout.rs" ins={5}
   pub enum Panel {
       View3d(Box<View3dSettings>),
       // ...
       Topics,
       Joints(JointsSettings),
   }
   ```

   The compiler then points at each match that needs an arm: `Panel::new` and `Panel::kind`, and
   reading and writing the file (`panel` and `RawNode::of`).

3. Draw it in `src/panels.rs` and add its arm to `body`. `key` is unique to the panel; prefix the
   keys of its children with it, because a layout can hold the same panel type twice. The panel's
   header (its name, settings button and menu) draws over the body's top when the pointer is on
   the panel, so start text `HEADER_H` down.

   ```rust title="src/panels.rs"
   fn joints(s: &State, view: &JointsSettings, key: &str) -> El {
       let Some((_, positions)) = s.joints() else { return empty("No joint states yet".into()) };
       let mut names: Vec<_> = positions.iter().filter(|(name, _)| !view.hidden.contains(*name)).collect();
       names.sort_by_key(|(name, _)| *name);
       let rows = names.into_iter().map(|(name, at)| text(format!("{name}  {at:.3}")).font(MONO_SMALL));
       scrolling(format!("{key}-scroll")).child(col().padding(12.0).pt(HEADER_H).gap(4.0).children(rows))
   }
   ```

4. Add its settings to `ui::panel_settings`. A `panel_lens` reaches this panel's settings by its
   path in the layout. Your `joints_settings` builds its controls from the ones in `src/ui.rs`
   (`toggle_row`, `picker`, `topic_switches`) and edits through the lens with `with`. A panel with
   no settings has no settings button: list it in
   `panels::has_settings`.

   ```rust title="src/ui.rs"
   Panel::Joints(view) => (None, joints_settings(s, view, &panel_lens(path, |p| match p {
       Panel::Joints(j) => Some(j),
       _ => None,
   }))),
   ```

5. If the panel needs topics nothing else subscribes to, add them in `State::wanted`
   (`src/app.rs`). Sources only deliver what's wanted.

</Steps>

Then `{"panel": "joints", "hidden": ["gripper"]}` works in a layout file.

## Add a source

Every source today is a Foxglove WebSocket server. Another transport, such as an MCAP file, would
be another implementation of `Source`:

```rust title="src/source.rs"
pub trait Source: Send {
    /// Replaces what the source delivers; returns at once.
    fn want(&self, wanted: Wanted);
}

/// What the app wants delivered: topics, and the colour choice (clouds are coloured while
/// decoding, off the UI thread).
pub struct Wanted {
    pub topics: HashSet<String>,
    pub color: ColorChoice,
}

/// Where a source sends its events, from its own thread.
pub type Sink = Arc<dyn Fn(Event) + Send + Sync>;
```

A source must:

- **Run on its own thread.** `want` returns immediately; I/O and decoding happen on a thread the
  source spawns. Dropping the source stops it.
- **Report status.** Send `Event::Status` with `Connecting`, `Connected { server }` (the name shown
  in the top bar), or `Failed { error }` (shown in the status chip). Retry if that makes sense
  for the transport.
- **Advertise channels.** Send `Event::Channels` with every topic it offers, each with its `kind`
  from `decode::decoder_for(encoding, schema, topic)`. Each list replaces the previous one.
- **Deliver only what's wanted.** Send `Event::Data` for topics in the latest `Wanted`, decoded with
  the same `decode::decoder_for` table. A message that fails to decode is `Event::DecodeFailed`.

Then pick it in `open`, which dispatches on the URL. `McapFile` here is hypothetical:

```rust title="src/source.rs" ins={2-4}
pub fn open(url: &str, sink: Sink) -> Box<dyn Source> {
    if let Some(path) = url.strip_prefix("file://") {
        return Box::new(McapFile::spawn(path.into(), sink));
    }
    Box::new(FoxgloveWs::spawn(url.to_string(), sink))
}
```

## Test a change

`cargo test` checks the decoders against bytes from the reference serializers
(`src/decode/testdata/`), and the robot's forward kinematics against pinocchio 4.1.0 on the same
URDF (`src/robot/testdata/med7.urdf`) in two poses.

The scripts render the app headless with Rune's tooling. They run `target/release/lantern`, so build
it first:

```sh
cargo build --release
scripts/snap-live.sh out/live "--cloud table" - settings top      # serve, then headless snapshots
scripts/snap-live.sh out/live "--cloud table" "-:--script scripts/interact.json"
scripts/audit-controls.sh      # every control must change the viewport (pixel diff vs baseline)
scripts/bench.sh 3             # timing table → out/bench.tsv, raw logs in out/bench/
```

- **`snap-live.sh OUT_DIR "SERVE ARGS" SCENE...`** starts the
  [replay server](/lantern/reference/replay-server/) with those arguments and renders
  each scene once data has arrived. `-` is the default state. Rune flags can follow a colon, as in
  `-:--script scripts/interact.json`, which drags, zooms and taps a control. Settings go to a
  throwaway config directory. Set `URL` to read another server, or `SETTINGS` to start from a
  whole `settings.json`:

  ```sh
  SETTINGS='{"layout": {"panel": "3d", "robot": {"urdf": "'$PWD'/fixtures/med7/med7.urdf"}}}' \
    scripts/snap-live.sh out/robot "--cloud table --robot-pose reach" - panel-settings
  ```

- **Scenes** (`--scene`) are `top`, `height`, `intensity`, `settings` and
  `panel-settings` (the 3D view's settings, open), plus the timing scenes `no-points`, `half`,
  `quarter`, `size-1` and `size-4`. Scenes don't save settings. Lantern's own flags work headless
  too: `"-:--layout dashboard"` snaps the dashboard preset.
